What “warm geo cache” means

We do not cache every GPS point. Neighbors in the same ~5 km geohash cell share one Redis entry for location sections. Warm = that entry (or L1 memory) already exists; cold = rebuild from Mongo.

Cold path

L1 miss → Redis miss → lock → Mongo queries for the bundle → fill L1 → defer Redis SET → return. Often ~1–3s+ for home.

Warm path

L1 hit (fastest) or Redis hit → assemble feed only. Typical local warm home ~0.7s avg in 20 VU tests.

One request from client → controller → three parallel bundles → feed assembly.

Three cache layers at a glance

Layer 1 · Shared

Global

Same for everyone on this env. No lat/lng, no userId.

  • Categories (if quickAction)
  • Banners
  • Global referral settings
  • Feed config gate
Redis 120s · L1 30s
Layer 2 · Neighborhood

Geo cell

Shared by users in the same geohash (~5 km) + tz/r/cat.

  • Near You · Top Picks · Trending
  • Popular Events · Newly listed
  • Tag groups · Pinned content
Redis 60s · L1 30s
Layer 3 · Personal

User

Keyed by userId. Exact location used in queries.

  • For You orgs & events
  • This week · Reservations
  • Custom cats · Highlights
  • Loyalty · Promotions
Redis 60s · L1 30s

Geohash: why Zagreb ≠ Lahore

Precision 5 ≈ 4.9 km × 4.9 km. Different cities get different geo= keys. Within one cell, everyone shares Near You / Popular / etc.

How much is dynamic?

Conceptual share of feed sections (not response bytes). Most browse content is geo-dynamic with a ~30–60s freshness window.

  • ~50% Geo — nearYou, popular, trending, topPicks, new, tags, pinned
  • ~35% User — forYou, thisWeek, reservations, loyalty, promotions…
  • ~15% Global — categories, banners, referral (+ live configs)
